# Как делался NOVA3 Bridge: разбор по шагам

English version: [PORTING_GUIDE.en.md](PORTING_GUIDE.en.md).

N.O.V.A. 3 — первый проект этого семейства. Здесь придуман сам способ: 32-битная игра исполняется в
`qemu-user` внутри APK, а её вызовы OpenGL ES уходят на настоящий GPU телефона. Поэтому руководство в
основном не про игру, а про три вещи, которые потом без изменений перешли в остальные проекты: как
запустить `qemu-user` в приложении Android, как устроен мост GLES и как искать, на что уходит время.

Каждый шаг описан одинаково: что было видно, как нашли причину, что и где исправили. Текущее состояние —
в [PROJECT_STATE.md](../PROJECT_STATE.md), сводка — в [README.md](../README.md), версии — в
[CHANGELOG.md](../CHANGELOG.md).

## Исходные условия

- Игра: N.O.V.A. 3 1.0.7, движок Glitch (Gameloft), библиотека `libNOVA3_neon.so`, ARM32 softfp.
- Телефон: OnePlus 13s, Snapdragon 8 Elite (ядра Oryon). Процессор исполняет только AArch64, системного
  транслятора ARM32 в прошивке нет (проверялось: `1554_Tango` в прошивке — это оператор связи, не транслятор).
- Основа: готовый порт N.O.V.A. 3 для PortMaster автора EapRules и его `portbase` — загрузчик bionic-ELF
  под glibc, переходники libc, фиктивный JNI. Этот порт рассчитан на ARM-консоль с 32-битным Linux; здесь
  он исполняется под qemu, а всё Android-специфичное дописано сверху.

## Часть 1. qemu-user внутри приложения Android

Четыре ограничения Android, на каждое из которых ушёл отдельный заход:

### 1.1. Исполняемый файл нельзя запустить откуда угодно

- **Видно:** запуск qemu из папки данных приложения запрещён системой.
- **Причина:** Android разрешает исполнять код только из каталога нативных библиотек приложения.
- **Исправление:** статический `qemu-arm` под AArch64 лежит в APK как `libqemu.so` и запускается из
  `nativeLibraryDir` через `ProcessBuilder`
  ([GameProcess.java](../port/android/src/com/jamescrumble/nova3/GameProcess.java)).

### 1.2. Seccomp убивает процесс за «лишние» системные вызовы

- **Видно:** процесс умирает с SIGSYS сразу на старте или на первом открытии файла.
- **Причина:** фильтр seccomp приложений пропускает только системные вызовы из белого списка bionic. Статический
  glibc внутри qemu вызывает `set_robust_list`, `rseq` и `faccessat2`. Последний приходит через `realpath()`,
  который qemu зовёт на каждом гостевом `open`.
- **Исправление:** [patch_syscalls.py](../port/android/patch_syscalls.py) переписывает места вызова в
  собранном бинарнике; в патче qemu `realpath()` оставлен только для путей, содержащих `proc`.

### 1.3. qemu молча не запускает гостя

- **Видно:** qemu завершается без сообщений.
- **Причины:** гостевая программа и её `ld.so` распакованы без бита исполнения; ошибки загрузки qemu
  печатает через `printf` и выходит через `_exit`, поэтому при перенаправленном выводе они теряются.
- **Исправление:** обёртка ставит бит исполнения после распаковки sysroot. Для таких случаев сделан
  `mstrace` (`port/android/tools/mstrace`), он достаёт текст ошибки из памяти процесса.

### 1.4. Отладочная сборка тормозит GL-поток

- **Видно:** поток, исполняющий GL-команды, занят проверками, а не работой.
- **Причина:** в отладочном APK включён CheckJNI.
- **Исправление:** в манифесте `debuggable=false`, для профилирования оставлено `profileable shell=true`.
  Там же `isGame` и `game_mode_config` с поддержкой режима производительности.

## Часть 2. Мост GLES

Игра вызывает GLES 2.0, но драйвера внутри гостя нет. Вызовы попадают в заглушки
[gl_bridge.cpp](../port/portbase/src/gl_bridge.cpp) (ARM32), кодируются в сообщения и пишутся в pipe. Поток
Java [GlBridge.java](../port/android/src/com/jamescrumble/nova3/GlBridge.java) читает их и исполняет через
`GLES30` на `SurfaceView`. Запросы, которым нужен ответ (`glGet*`, статус шейдера, `glReadPixels`), идут
через второй pipe.

Решения, принятые по ходу:

- **Имена объектов раздаёт гость**, хост переводит их в настоящие. Так `glGenTextures` не требует ответа.
- **Клиентские массивы вершин копируются в сообщение draw.** Это главный объём данных: 2–7 МБ на кадр.
- **Одна копия игры на процесс**: `singleTask`, полный `configChanges`, статический `GameProcess`. Иначе
  поворот экрана пересоздавал активити и запускал вторую игру.
- **Простые функции генерируются**: [gen_glbridge.py](../port/android/tools/gen_glbridge.py) пишет обе
  стороны моста из одной таблицы, чтобы коды операций не расходились.

## Часть 3. Слой игры

Это часть, унаследованная от порта для PortMaster; здесь перечислено, что в ней специфично для игры.

### 3.1. Защита GDRM

- **Видно:** `GL2JNILib.init()` падает на записи по нулевому указателю (`+0x008d3264`).
- **Как нашли:** указатель читается через GOT; слот ведёт на символ `lockPointer4`, рядом ещё три.
- **Причина:** на Android их заполняет активити-установщик после проверки лицензии на сервере, которого
  давно нет. Порт установщик не запускает.
- **Исправление:** четырём указателям выдана память — [patch.cpp](../port/game/patch.cpp). Код игры не
  правится.

### 3.2. Данные в OBB

- **Видно:** `assert false && "could not find sprites pack!"` на первом кадре.
- **Причина:** движок не читает OBB. На Android установщик распаковывает их в папку данных, и игра
  открывает обычные файлы.
- **Исправление:** [obb_cache.cpp](../port/game/obb_cache.cpp) достаёт файл из OBB при первом обращении к
  нему. Распаковка целиком означала бы 4 ГБ записи до титульного экрана.

### 3.3. Порядок вызовов

`setPaths` нельзя вызывать самому после `init()`: объект файловой системы ещё не создан, и вызов падает
внутри `glf::Fs::SetObbDir`. Движок сам вызывает `setupPaths` в Java, когда готов, и фиктивный класс
отвечает ему ([main.cpp](../port/game/main.cpp), [gl2jni_activity.cpp](../port/game/jni/gl2jni_activity.cpp)).

### 3.4. Профиль качества

- **Видно:** игра выбирает самый тяжёлый профиль графики.
- **Причина:** профиль выбирается по строке `GL_RENDERER`, а незнакомому GPU достаётся максимальный.
- **Исправление:** `gpu_name.txt` подменяет имя GPU. Профили лежат в зашифрованных архивах, поэтому
  [xml_hook.cpp](../port/game/xml_hook.cpp) перехватывает разбор XML: умеет сохранять документы и править
  их по списку замен.
- **Что не сработало:** флаг `HardwareSkinning` в движке мёртвый — поле никто не читает. Скиннинг
  выбирается по техникам материалов, подмена через XML эффекта не дала.

## Часть 4. Скорость

Исходная точка: бой шёл на 12–16 кадрах/с. Итог: до 55, с просадками от ограничителя частот.

### 4.1. Сначала измерить

Главный вывод диагностики: узкое место — **один поток**, главный поток игры внутри qemu (85–100 % ядра).
GPU-поток занят на 15–45 %, видеокарта простаивает. Ускорять нужно эмуляцию и всё, что заставляет главный
поток ждать.

Инструменты, сделанные для этого:

| Что | Чем |
|---|---|
| fps, число GL-команд, загрузка моста, ядро и частота | строка `[gl] frames` в логе раз в 5 с |
| профиль qemu на телефоне | `tools/profile.sh` (simpleperf), `tools/qemu_hot.py` |
| профиль кода игры | `QEMU_GUEST_PROF`, `tools/guest_prof.py`, `tools/prof_by_fps.py` |
| системные вызовы гостя | `QEMU_SYSCALL_STATS=1` |
| сравнение сборок qemu | `qemu/armbench.c`, `tools/bench_phone.sh` |
| длинные кадры | строка `slow frame` со счётчиками (`frame_stats.h`) |
| задержка касаний | строка `input:` раз в 600 кадров |

### 4.2. qemu

Профиль qemu показал: ~27 % времени — поиск блока при косвенных переходах, ~25 % — транслированный код,
~8 % — NEON. Правки (подробно в [qemu/README.md](../qemu/README.md)):

| Правка | Результат |
|---|---|
| VFP и преобразования float↔int одной командой процессора вместо softfloat | основа ускорения |
| NEON f32 на FPU телефона | после следующей правки |
| ленивое переключение FPCR | NEON в 6,7 раза быстрее: запись FPCR на Oryon очень дорогая |
| быстрый поиск блока для вызовов и возвратов | 1,7 раза на стенде |
| кэш переходов 4096 → 65536 записей | меньше промахов |
| вариант F: скалярный VFP прямо в сгенерированном коде, NEON целым регистром | VFP 200 → 160 мс, NEON 48 → 28 мс |

Точность не обсуждается на глаз: тесты `fptest.c`, `cmptest.c`, `neontest.c`, `neoncmptest.c` должны давать
те же хеши, что и чистый softfloat (`QEMU_STRICT_FP=1`).

Не добавлять SVE в `-march`: у Oryon его нет, получится SIGILL.

### 4.3. Библиотека игры

- **Видно:** ~13 % времени главного потока в функциях `__sync_*`.
- **Причина:** библиотека собрана под ARMv5 и для атомарных операций зовёт помощник ядра по адресу
  `0xffff0fc0`. qemu-user эмулирует его выходом из транслированного кода на каждом вызове.
- **Исправление:** литерал с этим адресом перенаправлен на маленькую процедуру на `ldrex/strex` —
  [tweaks.cpp](../port/game/tweaks.cpp). Отключается `NOVA3_FAST_CAS=0`.
- **Ловушка (0.6):** все 43 литерала лежат рядом с самими `__sync_*`, а их уже исполнили статические
  конструкторы. qemu-user защищает от записи страницы с транслированным кодом и обычно сам пропускает запись
  в них. На одном телефоне с Mali-G57 MC2 первая же запись (+0xbe6574) пришла в игру как SIGSEGV, хотя на
  Adreno 830 всё работало. Теперь перед записью эти страницы явно открываются через `mprotect` (qemu делает их
  записываемыми и сбрасывает их трансляции), а при отказе замена пропускается. Правило: в код модуля после
  того, как он начал исполняться, писать только после своего `mprotect`, и проверять его результат.

Там же: физика в отдельном потоке (под qemu каждый гостевой поток — отдельное ядро хоста) и свой угол обзора.

### 4.4. Мост

| Что было | Что сделано |
|---|---|
| мьютекс на каждом вызове | убран: GL у игры однопоточный |
| повторные `glUseProgram`, `glBindTexture`, одинаковые uniform | отсеиваются до отправки; uniform на кадр 1720 → ~290 |
| десятки запросов о шейдерной программе | один запрос при линковке |
| массив вершин копировался на каждый атрибут | interleaved-массив уходит одним блоком |
| для индексной отрисовки уходили вершины `[0, max]` | уходит диапазон `[min, max]`, границы кэшируются |
| `GlBridge.java` читал pipe двумя `read()` на команду | чтение крупными кусками в буфер 2 МБ |

Последняя строка дала больше всего. Профиль гостя показывал, что 43–63 % сэмплов главного потока в тяжёлой
сцене — один адрес, `svc 0` в libpthread: игра стояла в `write()` в pipe. После буферизованного чтения доля
упала до 2–4 %.

Ещё два источника лишних системных вызовов, найденные через `QEMU_SYSCALL_STATS`: SDL каждый кадр искал
`libudev.so` для опроса джойстиков (~730 `openat` в секунду) — подсистема джойстиков в режиме моста не
инициализируется; лог игры писал по три системных вызова на строку — оставлены только предупреждения и ошибки.

### 4.5. Кадры «в полёте»

Гость может обгонять хост на заданное число кадров. Значение 2 и pipe в 1 МБ дали заметно более ровный fps.
Цена — картинка отстаёт от ввода на два кадра.

### 4.6. Частота процессора — то, что не побеждено

- **Видно:** при одинаковой работе на кадр время кадра со временем растёт с 61 до 84 мс.
- **Как нашли:** в строку `[gl] frames` добавлены ядро, текущая частота и потолок. Температура ~53 °C,
  thermal status 0 — это не перегрев.
- **Причины, их две:** система срезает потолок частоты быстрых ядер до 1,2–1,4 ГГц из 4,32; и на главном
  потоке qemu, и только на нём, держит `uclamp.max` 171–319 из 1024, из-за чего регулятор считает поток
  ненагруженным.
- **Что пробовали:** режим игры `performance`, разрешение фоновой активности — помогает частично. Сброс
  `uclamp` из гостя (`sched_setattr`) возвращает EPERM. ADPF (`PerfHint.java`) на клэмп не влияет, по
  умолчанию выключен.
- **Что помогает:** убирать ожидания главного потока (пункт 4.4) и закреплять qemu на ядрах 6–7.

## Часть 5. Звук

- **Видно:** задержка звука растёт до ~0,75 с; щелчок примерно раз в 2 секунды.
- **Как нашли:** по логу и дизассемблеру `vox::DriverAndroid::CallbackOSL`.
- **Причины:** вывод через SDL спал 23 мс на период 23,2 мс и шёл на ~1 % быстрее реального времени —
  излишек копился в pipe и буфере. Движок держит в очереди два блока по 4056 байт, а SDL забирал по 4096 и
  добивал тишиной.
- **Исправление:** [opensles.cpp](../port/portbase/android/opensles.cpp) пишет блоки игры прямо в FIFO,
  темп задаёт динамик телефона. Pipe 4096 байт, буфер трека минимальный. При загрузке и в фоне в трек идёт
  тишина, а не сброс данных.
- **Проверка по логу:** `direct out - 100% of real time`, строк `speaker ran dry` нет.

## Часть 6. Что оказалось полезным правилом

1. **Сначала счётчик, потом правка.** Каждое ускорение начиналось со строки в логе, которая показывает
   проблему числом.
2. **Профиль гостя важнее профиля qemu.** «Главный поток стоит в `write()`» не видно в профиле эмулятора.
3. **Точность float проверяется тестом бит-в-бит**, а не картинкой.
4. **Ожидание выглядит для системы как простой.** Чем больше главный поток ждёт, тем ниже частота ядра.
5. **Перемещение установки под другое имя пакета** — это другое приложение для Android: нужен перенос
   сохранений ([SaveMigration.java](../port/android/src/com/jamescrumble/nova3/SaveMigration.java)).

## Что осталось

- Заставка на титульном экране рисуется в левом верхнем углу; причина не найдена.
- Выше 720p интерфейс игры ломается.
- Редкое зависание на экране загрузки, один раз, повторить не удалось.
- Просадки при появлении врагов: игра переоткрывает звуковой архив на каждый звук (120–220 открытий в
  секунду). Идея — держать `.gla` открытым в `symtab_io.cpp`; не сделано.
- Ограничение частоты системой (пункт 4.6).
